## 1. Executive Summary

### 1.1 한 줄 요약

**티업링크 운영팀이 클럽·라운딩·회원·고객문의를 한 흐름에서 "처리"하는 관리 콘솔** — 어떤 화면을 열어도 같은 방식으로 찾고, 고치고, 일괄 처리하며, 그 모든 행위가 기록된다.

### 1.2 핵심 지표

| 항목 | 내용 |
|------|------|
| 서비스명 | 티업링크 관리자 (teeup backoffice) |
| 목표 시장 | 내부 운영 (외부 판매 없음) |
| 타겟 사용자 | 티업링크 내부 운영자 (클럽장 등 외부 접근 영구 제외) |
| 핵심 가치 | 일관된 목록·일괄 처리로 운영 시간 단축, 감사 가능한 운영 |
| 수익 모델 | 직접 수익 없음. 앱 정기결제(토스 빌링) 운영 기반 제공 |
| 목표 기간 | 2026-10-28 ~ 2026-11-24 |

## 2. 서비스 배경 및 시장 기회

### 2.1 현황

| 항목 | 수치 | 출처 |
|------|------|------|
| 현행 화면 수 | 약 50 | 기존 `src/pages` |
| 현행 코드 규모 | 약 25,000줄 (최대 단일 화면 1,975줄) | 기존 `src/pages`, `src/lib/api` |
| 현행 로그 기능 | 없음 (콘솔 로깅만) | backend `routers/admin` |
| 현행 사용 빈도 | 사실상 0 — 개발자 본인도 복잡해서 미사용 | 소크라테스 세션 Q6 |
| 앱 운영 단계 | 지인 대상 실운영 시작 직전 | 소크라테스 세션 Q4 |

### 2.2 기회

- **실운영 전**이라 병행 운영 없이 한 번에 교체 가능 (마켓리서치 4.1)
- 대형 콘솔의 검증된 패턴(단일 목록 + 일괄처리 + URL 상태 + 타임라인)이 확립되어 있어 설계 리스크가 낮음 (마켓리서치 3.2)
- 인수 실사의 핵심 항목인 **감사 로그·권한·문서**를 운영 초기부터 갖추면 사후 보강 비용이 사라짐

### 2.3 레퍼런스 대비 포지션

| 대상 | 강점 | 약점 | 비고 |
|------|------|------|------|
| Shopify Admin | 목록 일관성, 일괄 작업 | 도메인 상이 | 목록 패턴 채택 |
| Stripe Dashboard | 이력 추적, URL 상태 | 도메인 상이 | 타임라인 채택 |
| 현행 teeup 백오피스 | 기능 범위 | 화면별 제각각, 로그 없음 | 교체 대상 |
| **신규 백오피스** | **일관성 + 처리 속도 + 감사 체계** | 초기 구축 비용 | 4주 내 교체 |

## 3. 타겟 사용자 정의

### 3.1 사용자 페르소나

**페르소나 A — 오너 운영자 (주 사용자)**

| 항목 | 내용 |
|------|------|
| 역할 | 티업링크 대표 겸 운영자, `SUPER_ADMIN` |
| 사용 환경 | 데스크톱 주 사용, 급한 처리는 폰 |
| 핵심 니즈 | 매일 처리할 일을 빨리 끝내기 (가입 승인, 문의 답변, 라운딩 관리) |
| 현재 해결 방식 | 백오피스를 쓰지 않고 DB 직접 수정 또는 개발 작업으로 처리 |
| 불만 사항 | 목록·필터·페이징·폼이 화면마다 달라서 복잡함 (1순위) |
| 기대 가치 | DB를 만지지 않고 3클릭 안에 처리 |

**페르소나 B — 역할 분리 관리자 (확장 사용자)**

| 항목 | 내용 |
|------|------|
| 역할 | CS 담당(`SUPPORT_ADMIN`), 콘텐츠 담당(`CONTENT_ADMIN`) 등 |
| 사용 환경 | 데스크톱 |
| 핵심 니즈 | 자기 담당 메뉴만 보고, 회원 문의 시 이력을 바로 확인 |
| 현재 해결 방식 | 없음 (운영 조직 확장 전) |
| 불만 사항 | 회원 행동 이력을 볼 수 없음 |
| 기대 가치 | 회원 상세 활동 타임라인으로 CS 즉시 대응 |

**페르소나 C — 인수 실사 담당 (간접 이해관계자)**

| 항목 | 내용 |
|------|------|
| 관심사 | 권한 체계, 감사 로그, 개인정보 처리 통제, 문서화, 코드 품질 |
| 기대 가치 | 누가 무엇을 조회·변경했는지 추적 가능, 산출물 체인 완비 |

### 3.2 사용자 세그먼트

| 세그먼트 | 비중 | 특성 | 우선순위 |
|----------|------|------|----------|
| 오너 운영자 | 현 단계 대부분 | 전 메뉴, 처리 중심 | P0 |
| 역할 분리 관리자 | 조직 확장 시 | 역할별 메뉴 | P1 |
| 시연 대상 (투자·인수) | 비정기 | KPI 대시보드, 마스킹 모드 | P2 |

## 4. 서비스 전략

### 4.1 핵심 가치 제안 (Value Proposition)

> **"어떤 화면을 열어도 같은 방식으로 찾고, 고치고, 처리할 수 있어서 업무 시간이 줄고 실수가 사라진다. 그리고 그 모든 처리는 기록된다."**

### 4.2 서비스 범위

| 구분 | 항목 | 우선순위 | 설명 |
|------|------|----------|------|
| 기반 | 공통 목록 시스템 | P0 | DataTable + FilterBar + 상태 탭, 필터·정렬·페이지 URL 보존 |
| 기반 | 일괄 처리 | P0 | 체크박스 선택 → BulkActionBar(승인·거절·상태변경·삭제) |
| 기반 | 로그 | P0 | 회원 활동 로그(우선, 1년 보관) + 관리자 감사 로그(변경·조회·다운로드) |
| 기반 | 인증·권한 | P0 | JWT+CSRF, 역할 6종 메뉴·라우트 가드, 서버 검증 |
| 업무 | 대시보드 "오늘 처리할 일" | P0 | 처리 큐 카드 → 필터 걸린 목록 직행 |
| 업무 | 회원 관리 | P0 | 목록·상세(탭)·활동 타임라인·생성·상태변경 |
| 업무 | 클럽 가입신청 | P0 | 대기 목록 일괄 승인·거절 |
| 업무 | 1:1 문의 | P0 | 미답변 기본 필터, 답변, 상태변경 |
| 업무 | 라운딩 | P0 | 목록·상세·생성·수정·팀 편성·점수·경비·통계 |
| 나머지 | 클럽 | P1 | 목록·상세 탭(멤버·공지·규정·회비·라운딩)·생성·수정 |
| 나머지 | 소셜 모임 | P1 | 목록·상세·생성·수정·경비 |
| 나머지 | 공지·FAQ | P1 | CRUD, FAQ 카테고리 |
| 나머지 | 관리자·프로필·설정·알림 | P1 | 관리자 CRUD(역할), 비밀번호, 설정, 헤더 알림 벨 |
| 나머지 | 감사 로그 조회 | P1 | 행위자·대상·기간 필터, 변경 전후 비교, 월간 점검 |
| 신규 | 신고·차단 | P1 | 신고 목록·처리, 차단 목록 |
| 신규 | 약관 | P1 | 버전 관리·게시, 회원별 동의 이력 |
| 신규 | 결제·구독(빌링) | P1 | 요금제, 구독, 결제 내역, 환불·재청구, 실패 건, 샌드박스 — 비활성 대기 |
| 신규 | KPI 대시보드 | P2 | DAU/MAU, 클럽·라운딩 수, 리텐션, 매출 추이 (운영 대시보드와 별도 탭) |
| 신규 | 마스킹 모드 | P2 | 이름·전화·이메일 일괄 마스킹 토글 (기본 OFF) |
| 제외 | RN 앱 수정, 외부 사용자, 다국어, 다크모드, 웹소켓, 외부 메신저 알림 | - | PRD "스코프 제외" |

### 4.3 차별화 전략

1. **처리 중심 대시보드**: 지표 나열이 아니라 "오늘 처리할 일" 큐. 카드를 누르면 필터가 걸린 목록으로 이동해 바로 일괄 처리
2. **예외 없는 일관성**: 모든 목록·폼·상태 표시를 공통 컴포넌트로 강제 (CLAUDE.md "백오피스 UI 규칙"), PR 템플릿에서 검사
3. **실사 대응 감사 체계**: 변경뿐 아니라 개인정보 조회·다운로드까지 기록, 수정·삭제 불가 (마켓리서치 2-5)
4. **객체 중심 상세**: 클럽·회원·라운딩 상세를 탭으로 묶어 화면 이동 최소화

## 6. 수익 모델

### 6.1 수익원 구조

백오피스 자체는 수익을 내지 않습니다. 앱의 향후 수익화(정기결제)를 **운영할 수 있는 기반**을 미리 만듭니다.

| 수익원 (앱) | 유형 | 백오피스 역할 | 상태 |
|-------------|------|---------------|------|
| 앱 구독 요금제 | 구독 (토스 빌링) | 요금제 관리, 구독·결제 내역, 환불·재청구, 실패 관리 | 구현 후 `BILLING_ENABLED=false` 대기 |
| 단건 결제 | 판매 (토스 일반결제) | 결제 내역 조회·취소 | 백엔드 기구현 (인증 헤더 버그 수정 필요, backend #48) |

### 6.2 가격 전략

요금제 금액·구성은 이 프로젝트에서 정하지 않습니다. 백오피스는 **요금제를 등록·수정할 수 있는 화면**을 제공하고, 실제 가격은 사업 결정 후 백오피스에서 입력합니다.

### 6.3 수익 시나리오

해당 없음 (내부 도구). 운영 효율 측면의 기대 효과:

| 시나리오 | 가정 | 기대 효과 |
|---------|------|-----------|
| 기본 | 운영 업무 전부 백오피스 처리 | DB 직접 수정 0건, 개발자 개입 없는 운영 |
| 확장 | 운영 인력 추가 | 역할 6종으로 권한 분리, 감사 로그로 통제 |
| 인수 | 실사 진행 | 감사 로그·권한·문서 즉시 제출 가능 |

## 7. 개발 전략

### 7.1 기술 스택 요약

> 프레임워크 V0.2 표준 스택 중 프론트는 그대로, 백엔드·인증·배포는 teeup 기존 인프라를 유지합니다 (CLAUDE.md "Tech Stack").

| 영역 | 기술 | 선정 사유 |
|------|------|-----------|
| 프론트엔드 | **React + Vite + TypeScript + Tailwind CSS** | 프레임워크 표준. 타입으로 API 응답 변화 감지, Tailwind는 사용자 선호 |
| UI 엔진 | TanStack Table, Radix UI, react-hook-form + zod | 헤드리스 — MUI 종속 해소, 스타일 완전 통제 (마켓리서치 2-7~2-9) |
| 서버 상태 | TanStack Query | 기존 사용 중, 캐시·재시도 표준화 |
| 백엔드 | **FastAPI + SQLAlchemy + MySQL** (기존) | 운영 중인 앱이 의존. 재작성 비용 대비 이득 없음 |
| 인증 | **자체 JWT + CSRF** (기존) | 기존 관리자 계정·토큰 체계 유지 |
| 인프라 | **Docker 빌드 → nginx 정적 서빙** (기존) | 현행 배포 파이프라인 유지 |
| 결제 | 토스페이먼츠 | 국내 PG, 빌링 지원 |
| 테스트 | Vitest + Testing Library | Vite 표준 |
