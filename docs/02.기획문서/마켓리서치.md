# 마켓 리서치 — 운영 콘솔 벤치마킹 (Market Research)

**프로젝트명**: 티업링크 백오피스 재구축
**작성일**: 2026-10-28
**버전**: v1.0
**대체 사유**: 백오피스는 외부 시장에 판매하는 서비스가 아닌 내부 운영 도구이므로, 시장 규모·가격 조사 대신 **운영 콘솔 UX 벤치마킹 + 구현 기술 조사 + 법규 요건**으로 대체합니다 (CLAUDE.md "Document Chaining" 메모).
**조사 방식**: 공개 문서·디자인 시스템 기반 정성 분석. 정량 수치는 출처가 확인된 경우에만 기재합니다.

---

## 1. 리서치 목적

- 질문 1: 잘 만든 운영 콘솔은 **목록·필터·일괄처리**를 어떻게 일관되게 만드는가? (1순위 페인포인트)
- 질문 2: 관리자 **감사 로그·권한**은 어떤 수준이어야 인수 실사·법규를 통과하는가?
- 질문 3: MUI 없이 Tailwind로 갈 때 쓸 **헤드리스 구현 기술**은 무엇이 성숙했는가?
- 질문 4: 정기결제(토스 빌링) 관리 화면에 무엇이 반드시 있어야 하는가?

## 3. 시장 분석 요약 (벤치마킹 요약)

### 3.1 시장 현황

| 항목 | 내용 | 출처 |
|------|------|------|
| 전체 시장 규모 | 해당 없음 (내부 도구) | - |
| 타겟 사용자 규모 | 내부 운영자 1~2인 (확장 시 역할별 분리) | PRD |
| 관련 앱 단계 | 지인 대상 실운영 시작 직전 | PRD |
| 성숙도 | 운영 콘솔 UX 패턴은 성숙기 — 표준 패턴이 확립됨 | 2-1 ~ 2-4 |

### 3.2 주요 트렌드

- **단일 목록 컴포넌트 + 일괄처리 바**가 대형 콘솔의 표준 (Shopify, Linear)
- **URL이 상태의 원천**: 필터·정렬·페이지를 쿼리스트링에 두어 공유·복원 (Stripe, Linear)
- **상세 화면 = 탭 + 타임라인**: 객체 중심으로 관련 정보와 이력을 한 화면에 (Stripe)
- **헤드리스 UI**: 스타일 내장 라이브러리에서 헤드리스(TanStack, Radix) + 유틸리티 CSS로 이동
- **감사 로그는 기본 기능**: SaaS 관리 콘솔에서 감사 로그·역할 권한은 엔터프라이즈 요건

### 3.3 경쟁 환경 (레퍼런스 비교)

| 레퍼런스 | 핵심 기능 | 강점 | 약점 (우리 관점) | 채택 요소 |

| Stripe Dashboard | 상세+이벤트, URL 필터, 역할 | 이력 추적 | 결제 특화 | 타임라인·URL 상태 |

## 4. 프로젝트 시사점

### 4.1 기회 요인

- 실운영 전이라 **빅뱅 교체 리스크가 최소** — 병행 운영 비용 없음
- 표준 패턴이 확립되어 있어 **설계 리스크가 낮음** — 검증된 패턴 조합으로 충분
- 공통 컴포넌트를 먼저 만들면 60화면의 한계비용이 급감

### 4.2 위험 요소

| 위험 요소 | 영향도 | 대응 방안 |
|-----------|--------|-----------|
| 법규상 관리자 접속기록(조회 포함) 미비 | High | 감사 로그에 조회·다운로드 포함, 1년 이상 보관, 월간 점검 화면 |
| 백엔드 목록 API의 페이징·필터 형식 불일치 | High | API 스펙 대조 후 공통 응답 형식(`items/total/page/size`)으로 정규화 — 프론트 어댑터 또는 백엔드 보강 |
| 빌링 오과금 | High | 비활성 기본값, 멱등키, 테스트 키 샌드박스 |
| 헤드리스 조합 초기 구축 비용 | Medium | 기반 단계에 집중 투자(#18), 이후 화면은 조립 |

### 4.3 차별화 기회

1. **처리 중심 대시보드**: 지표가 아니라 "오늘 처리할 일" 큐 → 필터 걸린 목록으로 직행
2. **목록 내 일괄 처리**: 가입 승인·문의 상태변경을 상세 진입 없이 완료
3. **실사 대응 감사 체계**: 변경·조회·다운로드 전부 기록, 위·변조 불가(수정·삭제 API 없음)
4. **마스킹 모드**: 시연·화면 공유 시 개인정보 일괄 마스킹
